# QANOW Constitution

QANOW는 회원이 질문을 남기고 관리자가 답변하는 질의응답 게시판이다. 본 헌장은 QANOW의 스펙·계획·
태스크·구현·리뷰 전 단계에서 지켜야 할 원칙을 정의한다. 각 원칙은 이름, 규칙, 이유, 검토 기준으로
구성되며, 규칙의 강제 수준은 MUST(반드시)·MUST NOT(금지)·SHOULD(권장)로 표기한다.

## Core Principles

### I. 역할 분리 (Role Separation)

**규칙**
- 사용자 역할은 비회원·회원·관리자 세 가지로 고정하며, 역할 × 행위 권한 표를 스펙에 명시적으로
  열거한다(MUST).
- 회원은 자신이 작성한 질문만 조회·수정·삭제할 수 있고, 답변을 작성할 수 없다(MUST NOT).
- 관리자만 전체 질문 목록 조회와 답변 작성·수정을 수행한다(MUST).
- 비회원이 보호된 화면이나 기능에 접근하면 로그인 안내로 유도한다(MUST).
- 역할 승격·부여 경로는 스펙에 정의된 방법 외에 두지 않는다(MUST NOT).

**이유**
역할 경계가 모호하면 타인의 질문 노출이나 무단 수정 같은 신뢰 훼손이 곧바로 발생한다. 역할과 허용
행위를 먼저 표로 고정해야 권한 검사·테스트·화면 분기가 같은 근거를 참조한다.

**검토 기준**
- 스펙에 역할 × 행위 권한 표가 있고, 모든 기능 요구사항이 그 표의 한 칸에 대응한다.
- 역할별 금지 행위마다 거부를 확인하는 테스트가 있다(타인 질문 접근, 회원의 답변 작성 등).
- 비회원의 보호 화면 접근 시 로그인 안내가 표시되는 테스트가 있다.

### II. 데이터 계층 권한 강제 (Authorization at the Data Layer)

**규칙**
- 권한 검사를 UI 숨김이나 클라이언트 분기만으로 끝내서는 안 되며(MUST NOT), 데이터 접근 계층
  (서버 API·쿼리·데이터베이스 접근 정책)에서 최종 강제한다(MUST).
- 모든 읽기·쓰기 경로는 요청자의 인증 정보와 자원 소유권을 서버 측에서 확인한다(MUST).
- UI의 권한 분기는 사용자 경험을 위한 보조 수단이며, 보안 근거로 인용할 수 없다(MUST NOT).
- 권한을 우회하는 관리 목적 경로를 두는 경우, 그 경로 자체도 데이터 계층 검사를 통과해야 한다(MUST).

**이유**
클라이언트는 조작할 수 있다. 데이터 계층이 최종 방어선이 아니면 주소 직접 입력이나 API 직접 호출로
권한이 무력화된다.

**검토 기준**
- 각 데이터 접근 경로마다 "어느 계층에서 권한을 강제하는가"가 `plan.md`에 기록되어 있다.
- UI를 거치지 않는 직접 요청(예: 타인 질문 식별자로 수정 요청)이 거부되는 통합 테스트가 있다.
- 권한 검사 없이 데이터에 접근하는 코드 경로가 리뷰에서 발견되면 병합을 막는다.

### III. 입력 검증 (Input Validation)

**규칙**
- 모든 사용자 입력은 서버(데이터 계층 포함)에서 검증하며, 클라이언트 검증은 중복 보조로만 둔다(MUST).
- 필드별 길이·형식·필수 여부의 구체적 기준은 스펙에 수치로 정의하고, 그 정의를 단일 출처로 삼아
  서버와 클라이언트가 함께 참조한다(MUST). 화면마다 다른 기준을 두어서는 안 된다(MUST NOT).
- 앞뒤 공백만으로 이루어진 입력은 빈 입력으로 취급한다(MUST).
- 검증 실패 시 어떤 필드가 왜 실패했는지 사용자에게 알리고(MUST), 서버 내부 예외나 스택 추적을
  노출하지 않는다(MUST NOT).
- 사용자 입력은 표시 시점에 이스케이프하여 스크립트 삽입을 막는다(MUST).

**이유**
검증 없는 입력은 빈 게시물·과대 입력·스크립트 삽입으로 이어진다. 검증 규칙이 여러 곳에 흩어지면
화면마다 동작이 달라지고, 어느 쪽이 진짜 기준인지 알 수 없게 된다.

**검토 기준**
- 경계값(0자·1자·최대치·최대치+1·공백만)에 대한 테스트가 모든 입력 필드에 있다.
- 검증 규칙이 한 곳에 정의되어 있고, 클라이언트가 그 정의를 재사용하거나 참조한다.
- 오류 메시지가 필드 단위로 표시되는 화면 테스트가 있다.

### IV. 명세 준수 (Spec Fidelity)

**규칙**
- 승인된 스펙에 없는 기능·화면·옵션을 임의로 추가하지 않는다(MUST NOT).
- 스펙의 범위 밖(Out of Scope) 항목은 구현하지 않으며, "확장 대비" 목적의 코드·스키마·설정도 두지
  않는다(MUST NOT).
- 스펙에 없는 요구가 필요해지면 먼저 스펙을 개정하고 승인을 받은 뒤 구현한다(MUST).

**이유**
스펙 밖 기능은 검토되지 않고 테스트되지 않은 채 들어와 범위와 일정을 흐리며, 원칙 XII의 추적성을
근본에서 깨뜨린다.

**검토 기준**
- 모든 태스크가 스펙의 기능 요구사항(FR) 또는 사용자 스토리(US) 식별자를 인용한다.
- 구현된 화면·API 중 스펙에 대응 항목이 없는 것이 하나도 없다.
- 범위 밖 항목에 해당하는 코드·스키마·화면이 없다.

### V. 세 핵심 화면의 일관성 (Consistency Across Core Screens)

**규칙**
- 세 핵심 화면(메인 페이지·질문 목록 페이지·질문 상세 페이지. 정확한 구성은 스펙이 확정한다)은 같은
  정보 구조(머리글·내비게이션·상태 표시·주요 행동 버튼의 위치)를 공유한다(MUST).
- 세 화면은 같은 디자인 토큰(색·타이포그래피·간격)과 같은 공용 컴포넌트를 사용한다(MUST).
- 같은 의미의 요소(질문 상태 배지·주요 버튼·오류 표시)는 세 화면에서 같은 모양과 같은 용어를
  사용한다(MUST). 화면별 고유 요소는 스펙의 "화면별 목적"에 근거가 있어야 한다(MUST).

**이유**
사용자는 세 화면을 하나의 흐름(작성 → 확인 → 답변 확인)으로 오간다. 화면마다 구조와 용어가 다르면
학습 비용과 오조작이 늘어난다.

**검토 기준**
- 공용 레이아웃과 공용 컴포넌트가 존재하고 세 화면 모두 이를 사용한다.
- 상태 용어와 배지 표현이 세 화면에서 동일하다(용어표 대조 기록).
- `plan.md`에 세 화면의 정보 구조 비교표가 있다.

### VI. 성능·가독성을 해치지 않는 시각 효과 (Visual Effects Within Limits)

**규칙**
- 메인 페이지의 시각 효과(배경 애니메이션·전환·장식)가 본문 텍스트의 대비와 가독성을 떨어뜨려서는
  안 된다(MUST NOT).
- 시각 효과는 핵심 콘텐츠(서비스 소개·질문 작성 유도·이용 흐름)의 표시를 지연시키지 않는다(MUST).
- 효과에 필요한 자산은 계획 단계에서 수치로 정한 성능 예산 안에서만 허용한다(MUST).
- 효과가 실패하거나 비활성화되어도 핵심 콘텐츠는 그대로 읽혀야 한다(MUST).

**이유**
메인 페이지의 목적은 서비스 이해와 질문 작성 유도이다. 효과가 목적을 가리면 본말이 전도된다.

**검토 기준**
- `plan.md`에 메인 페이지 성능 예산(초기 로드 크기, 주요 콘텐츠 표시 시점 등)이 수치로 있다.
- 효과 위에 놓인 텍스트의 대비를 계산해 접근성 기준(WCAG AA, 본문 4.5:1) 충족을 확인한 기록이 있다.
  육안 확인이나 시안 대조는 대비 검증의 근거가 되지 않는다.
- 효과를 끈 상태와 켠 상태 모두에서 핵심 콘텐츠가 동일하게 읽힌다.

### VII. 모션 감소 선호 존중 (Respect prefers-reduced-motion)

**규칙**
- 모든 애니메이션과 전환은 `prefers-reduced-motion: reduce` 환경에서 제거되거나 정적 대체 표현으로
  바뀌어야 한다(MUST).
- 정보 전달이 애니메이션에만 의존해서는 안 된다(MUST NOT). 모션 없이도 같은 정보를 얻을 수 있어야 한다.
- 자동 재생되는 반복 모션에는 정지 수단을 두거나, 모션 감소 설정에서 자동 정지한다(MUST).

**이유**
모션은 일부 사용자에게 어지러움과 집중 방해를 일으킨다. 운영체제 설정을 존중하는 것은 선택이 아니라
접근성의 기본이다.

**검토 기준**
- 모션 감소 설정을 켠 상태의 화면 테스트 또는 점검 기록이 세 화면 모두에 있다.
- 애니메이션을 정의한 모든 스타일 규칙에 모션 감소 대응 규칙이 짝으로 존재한다.

### VIII. 키보드 조작 보장 (Keyboard Operability)

**규칙**
- 회원가입·로그인·로그아웃·질문 작성·수정·삭제·답변 작성·수정 등 주요 행동은 마우스 없이 키보드만으로
  완료할 수 있어야 한다(MUST).
- 포커스 순서는 시각적 순서와 일치하고, 포커스 표시는 항상 보여야 한다(MUST). 포커스 표시를 제거하는
  스타일을 두어서는 안 된다(MUST NOT).
- 사용자 정의 컴포넌트는 표준 키 조작(Tab·Shift+Tab·Enter·Space·Esc)을 지원한다(MUST).
- 모달·오버레이는 열려 있는 동안 포커스를 내부에 가두고, 닫으면 원래 위치로 되돌린다(MUST).

**이유**
키보드 조작은 보조 기술 사용자와 숙련 사용자 모두의 기본 요구이며, 마크업 구조가 올바르다는 증거이기도
하다.

**검토 기준**
- 주요 사용자 시나리오마다 키보드만으로 수행한 테스트 또는 점검 기록이 있다.
- 포커스 표시를 숨기는 스타일이 없다.
- 사용자 정의 컴포넌트의 키 조작이 문서화되어 있다.

### IX. 색상에 의존하지 않는 상태 표현 (State Beyond Color)

**규칙**
- 질문 상태(답변 대기·답변 완료 등)와 시스템 상태(로딩·빈 목록·오류·권한 없음·저장 중)는 색상과 함께
  텍스트 레이블로 표시한다(MUST). 색상만으로 구분해서는 안 된다(MUST NOT).
- 아이콘만으로 상태를 표현하지 않으며, 아이콘에는 텍스트 또는 대체 텍스트를 함께 둔다(MUST).
- 상태 텍스트는 보조 기술에서도 읽혀야 한다(MUST).

**이유**
색각 이상 사용자와 흑백 출력 환경에서는 색상 차이가 사라진다. 텍스트는 모든 환경에서 살아남는다.

**검토 기준**
- 모든 상태 배지와 알림에 텍스트 레이블이 있다(색상 전용 표시 없음).
- 다섯 가지 시스템 상태(로딩·빈 목록·오류·권한 없음·저장 중) 각각의 텍스트 표현이 스펙에 정의되어 있다.
- 화면을 회색조로 변환해도 상태 구분이 유지됨을 확인한 기록이 있다.

### X. 데스크톱·모바일 시나리오 완주 (Cross-Device Scenario Completion)

**규칙**
- 핵심 사용자 시나리오(회원: 가입 → 로그인 → 질문 작성 → 상태 확인 → 답변 확인 / 관리자: 로그인 →
  대기 질문 찾기 → 답변 작성)는 데스크톱과 모바일 화면 폭 모두에서 완료 가능해야 한다(MUST).
- 모바일 폭에서 가로 스크롤이 발생하거나 주요 행동 버튼이 가려져서는 안 된다(MUST NOT).
- 기준 화면 폭은 계획 단계에서 데스크톱·모바일 각각 최소 한 개씩 수치로 고정한다(MUST).

**이유**
질문은 이동 중 모바일에서, 답변은 데스크톱에서 작성되는 경우가 많다. 한쪽에서만 동작하면 서비스 흐름이
끊긴다.

**검토 기준**
- `plan.md`에 기준 화면 폭이 명시되어 있다.
- 핵심 시나리오의 엔드투엔드 테스트가 두 화면 폭에서 각각 실행되고 통과한다.
- 모바일 폭에서 가로 스크롤이 없음을 확인한 기록이 있다.

### XI. 단순한 MVP 구조 우선 (MVP Simplicity First)

**규칙**
- 구조는 현재 스펙을 만족하는 가장 단순한 형태로 시작한다(MUST). 계층·패키지·추상화를 추가하려면
  계획 단계의 Constitution Check에서 정당화해야 한다(MUST).
- 외부 의존성은 기능 구현에 직접 필요한 것만 도입하고, 도입 사유를 `plan.md`에 남긴다(MUST).
- "나중에 필요할 것"은 구조 추가의 근거가 되지 않는다(MUST NOT).

**이유**
MVP 범위는 세 화면과 소수의 엔터티 수준이다. 과한 구조는 학습·검토 비용만 키우고, 쓰이지 않는 확장
지점을 만들어 원칙 IV 위반을 유도한다.

**검토 기준**
- `plan.md`의 Complexity Tracking에 정당화 없는 추가 계층·프로젝트가 없다.
- 의존성 목록의 각 항목에 사용 이유가 적혀 있다.
- 사용되지 않는 추상화·설정·기능 플래그가 없다.

### XII. 요구사항·디자인 추적성 (Traceability to Requirements and Design)

**규칙**
- 모든 구현 태스크는 스펙의 요구사항 식별자(FR·US)를 인용하고, 화면 작업인 경우 디자인 근거(화면별
  목적·정보 구조·디자인 토큰 정의)를 함께 인용한다(MUST).
- 근거를 인용할 수 없는 태스크는 생성하지 않으며, 필요하면 스펙이나 디자인 문서를 먼저 보강한다(MUST).
- 커밋 메시지 또는 병합 요청 설명에서 해당 태스크 식별자를 확인할 수 있어야 한다(MUST).

**이유**
추적성이 있어야 변경의 영향 범위를 알 수 있고, 원칙 IV(명세 준수)를 사후에 검증할 수 있다. 근거 없는
태스크는 대개 범위 밖 기능이다.

**검토 기준**
- `tasks.md`의 모든 태스크에 FR/US 식별자가 있고, 화면 태스크에는 디자인 근거 참조가 있다.
- 스펙의 모든 FR/US가 최소 하나의 태스크로 커버된다(역방향 확인).
- 커밋 이력에서 태스크 식별자를 추적할 수 있다.

### XIII. 실패한 작업은 완료가 아니다 (No Green, No Done)

**규칙**
- 테스트 또는 빌드가 실패한 태스크는 완료로 표시하지 않는다(MUST NOT). 완료 표시 전에 전체 테스트와
  빌드를 실행하고 결과를 확인한다(MUST).
- 검사 우회(`--no-verify`, 테스트 건너뛰기, 실패 테스트 비활성화, 오류 무시 설정)는 금지한다(MUST NOT).
- 실패 상태를 보고할 때는 실제 출력과 함께 사실대로 알린다(MUST). 확인하지 않은 것을 "된다"고 말하지
  않는다(MUST NOT).
- 로컬 통과만으로 배포 환경 동작을 단정하지 않으며, 배포 대상 환경에서 실제로 확인한 뒤 완료로
  본다(MUST).

**이유**
"거의 됐다"가 누적되면 어느 시점부터 깨졌는지 알 수 없게 된다. 완료의 정의를 녹색 상태로 고정해야
진행 상황을 신뢰할 수 있다. 로컬의 관대한 기본값은 배포 환경에서 터질 결함을 자주 가린다.

**검토 기준**
- 태스크 완료 표시 직전의 테스트·빌드 실행 기록(명령과 결과)이 있다.
- 비활성화되거나 건너뛴 테스트가 없다.
- 각 커밋 시점에 전체 테스트가 통과한다.

## 추가 제약 (Additional Constraints)

- 기술 스택(언어·프레임워크·데이터 저장소·인증 방식)은 `/speckit-plan` 단계에서 결정하고 `plan.md`의
  Technical Context에 기록한다(MUST). 본 헌장은 스택을 지정하지 않는다.
- 서비스는 로컬에서 의존성 설치 명령 하나와 실행 명령 하나로 기동되어야 하며(MUST), 상위 워크스페이스가
  사용 중인 포트 3777~3779는 피한다(MUST).
- 비밀값과 환경 변수 파일은 저장소에 커밋하지 않는다(MUST NOT). 비밀번호를 평문으로 저장하지
  않는다(MUST NOT).
- 배포 환경에서 값 없이 정의된 환경 변수는 빈 문자열로 주입될 수 있으므로, 필수 환경 변수는 기동 시
  존재와 비어 있지 않음을 함께 검사한다(MUST).
- 한국어 산출물(스펙·계획·README 등)은 문어체 "~이다" 종결을 기본으로 하고, 줄임말은 첫 등장 시 정식
  명칭을 풀어 쓴다(MUST).

## 개발 워크플로 및 품질 게이트 (Development Workflow & Quality Gates)

- 작업 순서: `/speckit-specify` → (필요 시 `/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks` →
  `/speckit-implement`. 계획 단계의 Constitution Check가 원칙 I~XIII의 검토 기준을 모두 다루어야
  태스크 단계로 넘어간다(MUST).
- 구현은 테스트 작성 → 실패 확인 → 구현 → 통과 → 커밋 순서를 따른다(MUST).
- 커밋은 사용자 스토리 단위로 묶고, 커밋 시점에 전체 테스트와 빌드가 통과해야 한다(MUST, 원칙 XIII).
- 접근성 점검(원칙 VI~IX)은 육안 확인으로 대체할 수 없으며, 대비 계산과 자동 검사 도구 결과를
  기록으로 남긴다(MUST). 디자인 시안과 접근성 기준이 충돌하면 접근성 기준을 따른다(MUST).
- 리뷰 체크리스트: (1) 원칙 I·II 권한 표와 데이터 계층 강제, (2) 원칙 III 경계값 테스트,
  (3) 원칙 IV·XII 스펙 대응과 추적성, (4) 원칙 V~X 화면·접근성 점검 기록, (5) 원칙 XI 복잡성 정당화,
  (6) 원칙 XIII 녹색 상태 확인.

## Governance

- 본 헌장은 QANOW의 다른 모든 관행·지침보다 우선한다. 충돌하면 헌장을 따르거나 헌장을 개정한다.
- 개정 절차: 변경 사유와 영향 범위를 기술한 제안 → 사용자 승인 → 본 문서 수정과 버전 갱신 →
  `.specify/templates/` 및 관련 스킬 지침과의 정합성 확인. 개정 내용은 상단 Sync Impact Report에
  기록한다.
- 버전 정책(시맨틱 버저닝): MAJOR는 원칙의 삭제·재정의 등 하위 호환 불가 변경, MINOR는 원칙·섹션 추가
  또는 실질적 확장, PATCH는 문구 명확화·오탈자 수정 등 비의미적 변경이다.
- 준수 검토: 모든 `/speckit-plan` 산출물의 Constitution Check와 모든 코드 리뷰에서 원칙 I~XIII의 검토
  기준을 확인한다. 위반 사항은 수정하거나, 정당화 사유를 `plan.md`의 Complexity Tracking에 남겨야 한다.
